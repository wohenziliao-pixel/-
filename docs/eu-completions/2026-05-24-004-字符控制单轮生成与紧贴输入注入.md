# 字符控制单轮生成与紧贴输入注入

## 任务

用户反馈「字符控制」不生效、回复 token 偏短；且目标在单轮上限 2048 以内时，应靠**首轮生成**（`max_tokens` + 提示词位置）约束，而不是靠续写第二轮补长。

## 根因

1. 字符控制原先放在 `optionalSystem` 最前，经 `normalizeStMessageOrder` / `toBackendSafeMessages` 后远离本轮输入，模型易忽略。
2. 「新增规则」虽标为作者注释深度，但 `role: system` 的中间插入同样会被提到 system 前缀，深度注入实际失效。
3. `euApplyLiveProfileMaxTokens` 固定用预设 2048，未按目标为首轮预留 completion 预算；偏短时依赖 `shouldAutoContinueReply` 续请求。

## 改动

- `public/eu.html`（构建戳 `20260524-character-control-single-round-v146`）
  - 字符控制：以 `user` 指令插在**本轮用户输入正前方**（`applyCharacterControlBeforeUserTurn`），优先级高于深度 4 的「新增规则」。
  - 新增规则：改为 `user` 角色的系统指令块，保留深度 4 插入，避免被提到最前 system 块。
  - 首轮 `max_tokens = min(预设上限, 字符控制 maxTokens 区间上限)`；手动续写/嵌套续写仍用预设上限。
  - 字符控制开启时关闭「偏短再续写」路径（`canEuAutoContinueSecondRequest` / `shouldAutoContinueReply`）。
  - 弹窗说明、`dumpEuStorybookPromptAudit` 增加字符控制字段。

## 自测

1. 硬刷新后确认 `document.documentElement.dataset.euClientBuild` 为 `v146`。
2. 开启字符控制，目标如 800，发一条消息。
3. Network → `generate`：`max_tokens` 约为 `ceil(800×1.12)`；`messages` 中在本轮 user 前应有「字符控制」指令。
4. `dumpEuStorybookPromptAudit()`：`characterControlUsesSecondRequest` 应为 `false`。
5. 不应再因偏短自动出现第二次 `generate`（除非关闭字符控制且仍勾选旧续写逻辑）。
