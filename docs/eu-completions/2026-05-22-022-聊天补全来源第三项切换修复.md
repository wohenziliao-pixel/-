# 聊天补全来源（第三项）随 API 配置切换修复

## 问题

两条 API 连接配置在第三项「**聊天补全来源**」（OpenRouter / Custom / xAI 等）上应是完全不同的选项，后续 API 密钥、模型、URL 表单项都依赖该项。切换配置时第三项未正确切换，导致后面整段表单填错（例如 DEEPSEEKV3 应为 OpenRouter，却仍显示或沿用其它来源下的字段）。

## 根因

1. 整表重置时先把 `chat_completion_source` 写成默认 **OpenAI**，再覆盖，中间状态与 `reconnectOpenAi` 竞态。
2. 应用时以过期的 `connectionSnapshot` 为准，未强制以配置条目的 **`profile.api`**（即保存时的聊天补全来源）为准。
3. `setChatCompletionSourceQuiet` 未走与手动切换相同的 `change` 事件链，显隐与后续字段不同步。

## 改动

- `buildFullStateFromProfile()`：`profile.api` 优先决定 `chat_completion_source`。
- 重置时**跳过**第三项，清空其它连接字段后，**单独** `setChatCompletionSourceQuiet(目标来源)`，再填该来源下的模型/URL 等。
- 保存/更新配置时同步 `profile.api` 与 `connectionSnapshot.chat_completion_source`。
- 对 OpenRouter / Custom / xAI / Z.AI 在连接成功后分别写入对应模型与 URL 控件。

## 用户自测

1. 硬刷新页面。
2. 每条配置：设对第三项来源及下属字段 → **更新配置** 或 **连接** 成功。
3. 在 DEEPSEEKV3（OpenRouter）与 GLM（Custom 或 Z.AI）等之间切换：第三项应立刻变为对应来源，下方只出现该来源的表单块。
