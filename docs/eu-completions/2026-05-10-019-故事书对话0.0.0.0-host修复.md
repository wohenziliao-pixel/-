# 故事书对话 0.0.0.0 host 修复

## 任务

EU 故事书对话失败：控制台出现对 `http://0.0.0.0:8000/api/backends/chat-completions/generate` 的请求，并伴随超时或 400；要求**不修改酒馆核心**，仅在 EU 侧处理。

## 原因说明

- 若 SillyTavern 或书签使用 **`http://0.0.0.0:port`** 打开静态页，浏览器对相对路径 `fetch('/api/...')` 会继承该 host；`0.0.0.0` 作为 HTTP 目标在常见浏览器下**不可靠**，易出现长时间挂起（表现为客户端 `>45s` 超时）。
- 若 API 预设里 **`custom_url` / `reverse_proxy`** 写成 `http://0.0.0.0:8080/...`，EU 原样带给 `/api/backends/chat-completions/generate` 后，由酒馆 Node 转发上游时也可能异常。

## 改动

- `public/eu-demo.html`
  - 新增 `normalizeEuFetchUrl`：当页面 origin 的 host 为 `0.0.0.0` 时，将发往本站的 API 请求解析为 **`http://127.0.0.1:同端口/...`**。
  - 新增 `sanitizeZeroHostInHttpUrlString`：把 URL 串中的 host `0.0.0.0` 替换为 `127.0.0.1`。
  - `ensureStCsrfToken`、`stApiRequest`、`euPublicJsonPost`、`euTiebaMutate`、贴吧相关直连 `fetch`、`requestAiReplyStream` 中的 generate 请求统一走 `normalizeEuFetchUrl`。
  - `fetchStLiveGenerationProfile` 与 `buildStGeneratePayload` 对 `custom_url` / `reverse_proxy` 做零地址清洗。
  - 更新 `EU_CLIENT_BUILD_STAMP` 便于确认静态资源已刷新。

## 用户自测

1. 硬刷新（或禁用缓存后刷新）`eu-demo.html`，在控制台执行 `document.documentElement.dataset.euClientBuild` 应看到新 stamp。
2. 若仍从 `0.0.0.0` 书签进入，故事书发送应不再长期卡在 generate；**更稳妥**是收藏夹改为 `http://127.0.0.1:8000/...`（避免 Cookie 与 host 不一致的边界情况）。
3. 若仍有 400，请看 Network 里该 POST 的响应体（多为酒馆/上游 API 配置问题），与本次 host 修复无关时再单独排查。
